# 2.9 Directory sync: plan

Spec: `docs/superpowers/specs/2026-11-10-directory-sync-design.md`. One pull request per issue.

**Goal:** a folder of profiles becomes reviewed, consented updates to an organization's directory: first as files an administrator uploads, then through the directories' own APIs.

## Task 1: design spec (#30)

- [x] Spec written, with the brainstorm's questions decided on a recommendation and listed for confirmation.

## Task 2: batch runner (#31)

- [x] `lib/directory/` : read a folder of profiles and bundles; build each person's release; match to a directory user; compare field by field under the authority table.
- [x] `turnrow-profile directory diff <folder> --against <export> --target <connector> --domain … --method … --out <folder>` writes per-person change files, the combined change set, `report.md`, `refusals.json` and the consent receipts.
- [x] Refusals: no consent, no active directory audience for the domain, no matching user, more than one matching user, an invalid profile.
- [x] A neutral `scim` connector (reads a SCIM list, renders SCIM PatchOp files) so the runner is tested end to end before any vendor connector exists.
- [x] Nothing is applied by `diff`. `directory apply` is added with the first API connector.

## Task 3: Google Workspace bulk CSV (#32)

- [x] Columns confirmed on 2026-11-10 from Google's help page "Add or update multiple users from a CSV file" (https://knowledge.workspace.google.com/admin/users/add-or-update-multiple-users-from-a-csv-file, updated 2026-10-26): the five required columns, `****` to keep a password, an empty optional cell keeps the directory's value, UTF-8 with a byte-order mark for non-ASCII text. The page does not list every optional column; the console's downloadable template is the authority for those.
- [x] `google-csv`: reads the console's user export, renders the upload file with only the changed users and columns it may set (first name, last name, work phone).
- [ ] Not done: tested against a recorded export. No real export was available; the fixture is written by hand from the documented headers. A header row from a real export (no data needed) would close this.

## Task 4: Google Directory API (#33)

- [x] Confirmed on 2026-11-10 (https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/patch): `PATCH https://admin.googleapis.com/admin/directory/v1/users/{userKey}`, scope `https://www.googleapis.com/auth/admin.directory.user`. Patch cannot clear repeated fields, and Google recommends `update` for some uses; this connector patches only `name.*` and a custom schema, and writes no repeated field.
- [x] `google`: the requests, and `directory apply` (dry run by default; approval by hash; re-read before write; audit log; rollback file), in `lib/directory/api.mjs`.
- [x] Photos: `users.photos.update` in a request of its own, with the hash kept in the custom schema.
- [ ] Not done: a service-account flow (the administrator supplies an access token), creating the custom schema, and a run against a real tenant.

## Task 5: Microsoft Entra ID (#34)

- [x] Confirmed on 2026-11-10 (https://learn.microsoft.com/en-us/graph/api/user-update?view=graph-rest-1.0, updated 2026-07-04): `PATCH /users/{id}` returns 204; least-privileged application permission `User.ReadUpdate.All`; phones need `User-Phone.ReadWrite.All`.
- [x] `entra`: reads a Graph user list (with `manager` expanded, if present); plans `PATCH /users/{id}`; extension attributes through `--map`.
- [x] Decided, not built: Entra's API-driven inbound provisioning (`bulkUpload`). It creates and updates users from an HR source, and a sync here never creates a user or writes the employer's fields. The Graph connector is the way to update Entra.
- [ ] Not done: a run against a real tenant. The manager link is the employer's, so it is only compared.

## Task 6: Okta (#35) and Task 7: OneLogin (#36)

- [x] Okta, confirmed on 2026-11-10 (developer.okta.com, "Update a user"): `POST /api/v1/users/{id}` is a partial update (`PUT` nulls what is not sent); scope `okta.users.manage`.
- [x] OneLogin, confirmed on 2026-11-10 (developers.onelogin.com, Users API v2 "Update User"): `PUT /api/2/users/{id}` with only the fields to change; a bearer token from credentials with "Manage users"; custom attributes must already exist.
- [x] `okta` and `onelogin` on the same executor; custom attributes through `--map`.
- [ ] Not done: a run against a real tenant of either.

## Task 8: LDAP / Active Directory (#37)

- [x] Attribute map settled (in `lib/directory/ldif.mjs`): `givenName`, `sn`, `displayName`, `telephoneNumber` are written; `title`, `department`/`departmentNumber`, `division`, `employeeNumber`/`employeeID`, `manager`, `physicalDeliveryOfficeName` are read and compared.
- [x] `ldif`: reads an LDIF export, renders `changetype: modify` records. Applying is `ldapmodify`'s job.
- [x] `jpegPhoto` from the person's bundle (JPEG only), compared by hash.
- [ ] Not done: Active Directory's `thumbnailPhoto` (100 kB at most, so it needs resizing), and a run against a real directory.

## Task 9: other directories (#38)

- [x] Triage, with no code. Issue #38 stays open to collect demand.

| Directory | What it would take | Note |
|---|---|---|
| JumpCloud | A connector like `okta`: its Users API takes a partial `PUT /api/systemusers/{id}`; custom attributes are a list | Confirm the API from JumpCloud's documentation first |
| PingOne / PingDirectory | PingOne has a Users API (`PATCH`); PingDirectory speaks SCIM and LDAP | The `scim` and `ldif` connectors may already serve PingDirectory |
| Rippling, Workday, BambooHR and other HR systems | These are sources of the employer's fields, not places to push a person's fields | They belong with write-back (HR system to profile), not with sync |
| Any directory with SCIM 2.0 | Nothing: use `--target scim` | The bulk file needs a `/Bulk` endpoint; where there is none, one PATCH per user is the same data |
